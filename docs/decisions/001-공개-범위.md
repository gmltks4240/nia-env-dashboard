# 001. 실적 데이터는 공개로 두고, 수정 권한과 회원 정보만 막는다

날짜: 2026-11-24

## 무엇을 정했나

리포지토리를 public 으로 유지하고, Supabase 의 실적 데이터(`energy`, `waste`,
`env_metrics`, `env_settings`)도 **로그인 없이 읽을 수 있는 상태 그대로 둔다.**

수정 권한과 회원 정보는 지금처럼 막아 둔다.

## 그때 상황

오픈소스로 공개하는 과제인데, 과제 조건에 "영업 비밀이나 회사의 비밀 정보를
절대로 사용해서는 안 됨" 이 있었다. 공개 전에 무엇이 노출되는지 점검했다.

점검 결과:

- 리포지토리는 이미 public 이고, 스타·포크·워처 모두 0 (아직 아무도 받아가지 않음)
- `js/core.js` 에 Supabase URL 과 anon 키가 들어 있음
- `supabase/auth_roles.sql:160, 173` — `anon`(비로그인) 에게 실적 테이블 `select` 허용,
  정책은 `using (true)` 로 조건 없음. **즉 로그인 없이 전체 조회가 가능**
- 쓰기(insert/update/delete)는 로그인 + `editor`/`admin` 권한 필요
- `change_log`, `app_users` 는 로그인 필요, 관리자 또는 본인 것만
- 커밋 히스토리 전체를 디코딩해 확인한 결과 **`service_role` 키는 유출 없음.
  존재하는 토큰은 `anon` 하나뿐**

## 고려한 선택지

### A. 익명 읽기를 막는다 (`revoke select ... from anon`)

- 장점: 노출 자체가 사라짐. 가장 보수적
- 단점: 비로그인 열람 기능을 잃음
- 비용은 거의 없음 — `js/main.js:1046` 에 익명 읽기가 막혔을 때
  로그인 화면으로 안내하는 처리가 이미 있어서 코드 수정이 필요 없음

### B. 데이터를 합성 샘플로 전부 교체한다

- 장점: 실제 수치가 아예 사라짐. 데모로 쓰기도 좋음
- 단점: 운영 중인 시스템의 데이터를 지울 수는 없으므로, 공개용과 운영용을
  분리해야 함. 작업량이 큼

### C. 그대로 둔다 (선택)

- 공공기관의 에너지 사용량·온실가스 배출량은 상당 부분 이미 공시 대상
  (알리오, 공공부문 온실가스 목표관리제 이행실적). 숨겨야 할 성격의 자료가 아님
- anon 키는 Supabase 설계상 **공개를 전제로 한 키**다. 브라우저에 담기므로
  숨길 수 없고, 그래서 RLS 로 막는 구조다. 공개된 것 자체는 설계대로이며
  재발급할 이유가 없다 (`service_role` 이었다면 즉시 재발급 대상)
- 수정·삭제는 막혀 있어 데이터가 훼손될 수 없음

## 고른 이유

노출되는 것이 공시 수준의 자료이고, 훼손 경로가 없으며, 익명 읽기는 의도된
동작이었다. 막아서 얻는 것보다 그대로 두는 편이 단순하다.

## 감수하는 것

- 누구나 리포에서 키를 복사해 실적 데이터 전체를 내려받을 수 있다
- 월별·사업장별 세부 수치까지 공시 대상인지는 확인하지 않았다.
  기관 담당자가 아니라고 판단하면 선택지 A 로 즉시 전환할 수 있다 (SQL 한 줄)
- 회원가입은 누구나 할 수 있다. 승인 전에는 권한이 없으므로,
  `데이터 관리` 탭의 승인 대기 목록에 모르는 사람을 승인하지 않는 것으로 관리한다

## 이 결정을 되돌리려면

```sql
revoke select on public.energy, public.waste, public.env_metrics, public.env_settings
  from anon;
```

정책에서도 `anon` 을 빼면 된다. 화면은 자동으로 로그인 요구로 바뀐다.
